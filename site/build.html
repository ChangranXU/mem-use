Add an agent harness

A harness runs the agent’s task input, model requests, tools, and stopping logic. Choose who controls memory execution:

  • Your loop controls memory: use shared_bridge.Session. Map task boundaries, reads, directed actions, exposure receipts, and closure to the bridge lifecycle.
  • A native plugin or service controls memory: preserve that loop. Report observed operations through shared_bridge.observed and EpisodeAnnotator.

For the Session path, check each result and close scopes in order. A prepared delivery is not proof of consumption: use NOT_EXPOSED only when non-delivery is known, and UNKNOWN when evidence is insufficient.

The harness tutorial includes a runnable example, multi-turn call order, failure handling, and recorder wiring. It also explains how to connect application tasks outside the supplied benchmarks.

Record evidence for MemUse

Bridge trace sinks record lifecycle events. They do not capture model traffic. MemUse needs schema-10 recorder data with explicit memory_* annotations.

  • Open episode scope before model traffic, and keep agent and memory-model lanes distinct.
  • Bind each delivery to its consuming call and exact placement. A bridge input hash alone does not prove what crossed the API boundary.
  • Retain search results even when they were not delivered. Preserve the exposed subset and full source provenance.
  • Record confirmed writes and incomplete evidence separately. Never treat an uncertain mutation as a confirmed write.

Use the annotation contract with the MemUse input requirements. Session hosts also need request-placement hooks; installing a trace sink alone is insufficient.

Verify the integration

Use offline service doubles and scripted agent traffic to check isolation, native schemas, publication, consuming-call attribution, failure handling, and credential masking. Run the affected package tests before a live sample.

Then qualify the actual integration with an authorized live run. A writable system needs at least one write and a later recall; a read-only corpus needs relevant and no-match cases. A successful task with no memory operations does not verify the integration.

Check each recording with the recorder verifier, from the memory-bridge root:

uv run --project ../extension/traj-recorder python \
  ../extension/traj-recorder/tests/verify_trajectory.py path/to/recorded-run

Replace the path with one recorder directory. Next, follow the offline evidence check. Report skipped checks and unverified combinations in your contribution.

Develop MemUse

After installing MemUse’s Python and agent dependencies, run the relevant offline tests from mem-use:

uv run pytest tests/test_injudge.py -q
uv run pytest tests -q

For code changes, use the focused file while iterating and run the full suite before a code PR. For prose-only edits, check links, commands, and the diff. See development for the module map and checks.

Judge prompt changes need calibration. Canned responses test the contract. Use authorized real-judge runs to assess judgment quality, and report disagreements and stability.

Report bugs or questions in the relevant project: MemUse, memory-bridge, or traj-recorder. Read the bridge contribution guide or MemUse repository rules before a PR.
