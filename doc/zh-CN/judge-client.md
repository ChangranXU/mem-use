# 评审智能体

[文档目录](README.md) · [English](../en/judge-client.md)

评审是构建在 [pi](https://github.com/earendil-works/pi) agent 运行时（`@earendil-works/pi-agent-core` + `@earendil-works/pi-ai`）上的智能体，由一个小型 TypeScript 运行器（`agent/runner.ts`）驱动，Python 为区间对话的每个阶段（首次调查，以及每次答案被拒后的跟进）各生成一个进程，各进程通过 `job.history` 延续同一条对话。

Python 拥有判定契约；运行器拥有对话。

端点设置见[配置](configuration.md)（先执行一次 `npm --prefix agent install`；PATH 上需要 node ≥ 22.19）。

## 对话

一个区间、一条对话，作用域限定在其所属 episode。Python 物化该区间的[证据文件夹](scoring-input.md)，从五信号 rubric 组装系统 prompt，写出一个不含密钥的作业文件；运行器用且仅用两个证据工具构建 pi 智能体。开场消息包含确切的目标区间、紧凑文件导航，以及来自 manifest 的必读清单；详细索引与 episode 文件仍可由工具读取。

`read_evidence` 每次调用可读取多个完整文件（`paths`），因为每次模型调用都会重发整个对话：读取一个足迹窗口只需一次调用，而不是每个步骤一次。结果文件返回保留与已执行的调用计数、上报用量（含被回滚的轮次）与上下文回滚。

操作的 `input` 汇总各阶段已执行的 LLM/工具调用、上报用量与上下文回滚，保留最后一个阶段的保留调用计数，并携带最终的 `forced` 与任意阶段强制的 `any_phase_forced` 标记；停止原因留在轨迹中。

调用数必须是非负整数。缺失或格式错误的计数记为 null；某阶段没有返回结果时，
其保留调用数也记为未知。

## 轨迹记录

每条对话都以 pi 事件流的形式记录为轨迹：运行器订阅智能体的事件流，把每条完成的消息即时追加到 `<output>/<run-stamp>/agent-runs/<span-dir>.jsonl`。每个区间一个 JSONL，每次评判运行整体替换；每行为 `{seq, type, …}`，`seq` 在 attempt 内局部编号：

- `attempt`——开启每个运行器进程的行；attempt 1 为首次调查，之后均为跟进。各阶段追加到同一文件；种入的 history 不触发事件，因此不会重复。
- `message`——一条完整消息（用户开场、含工具调用与单次调用用量的 assistant 回合、工具结果），包括随后被预算回滚的回合。
- `tombstone`——`{removedSeqs, reason}`：上下文预算回滚（`context_budget_rollback`）或强制作答轮被剥离的工具尾巴（`forced_tool_tail`）从存活对话中移除了什么。
- `attempt_end`——答案、停止原因、forced 标记、错误、保留对话的计数/用量，以及本阶段已执行的调用/用量与回滚。只有后者会在各阶段间汇总。

强制作答消息经上下文重写进入对话（不触发事件），运行器会把它显式追加进轨迹。运行器在写入每条记录之前对凭证回显打码。Python 在每次尝试后再次检查文件，并移除不完整记录。操作的 `input.transcript` 以相对于运行文件夹的路径指向该文件——`agent-runs/<span-dir>.jsonl`。

强制答案若同时包含被阻止的工具调用，运行器在为工具尾部写入 tombstone 后重新记录保留的 assistant 文本，确保回放仍包含最终答案。

## 预算与强制作答

首次付费调用前，运行器估算开场消息、系统提示词、工具 schema 和全部
`required_reads.always` 文本的大小。若估算值超过输入预算，就拒绝该区间。
估算不含空行、读取格式和可选证据；通过此检查不代表完整调查一定能放入上下文。
输入预算包含 pi 的上下文预留，因此预检与实际发送请求的库使用相同边界。

对话开始后，两个预算可以通过**强制作答**结束对话：

- **步数预算**（`MAX_STEPS`）：LLM 调用数达到上限时，对话被截为最后一个作答轮：强制作答消息告知智能体预算已耗尽，要求它停止调用工具，并基于已收集的证据立即写出最终答案；强制作答轮里任何违抗的工具调用都会被拦截。
- **上下文预算**（`CONTEXT_WINDOW`）：使用最近一条适用的 assistant usage 加上后续消息估算；没有可用输入用量时（含只有输出用量的响应），根据消息、系统提示词和工具 schema 估算。水位线包含 pi 的上下文预留、`MAX_OUTPUT_TOKENS` 和强制作答消息的估算大小；越过水位线时回滚溢出轮次并注入强制作答消息。

答案被拒后的跟进**最多使用四次模型调用，包含最终作答**；若 `MAX_STEPS` 更低则服从该值。四次上限允许最多三轮取证和一轮强制作答，不会重新获得完整的首次调查预算。既有上下文水位线仍可能更早触发强制作答。这是固定策略，不增加配置项。

跟进期间，运行器在每轮工具调用后重新计算输出余量，保留放得下的新证据，并相应降低输出上限，最高为 `MAX_OUTPUT_TOKENS`。上限不得低于该区间最短允许答案的估算大小；开场上下文无法留下这部分空间时，在付费调用前拒绝。超出剩余预算的读取仍会回滚，被拒答案的历史保持不变。该估算不保证答案完整或正确。

在调查成果仍被保留的情况下，强制作答可以是有效判定。若对话中仍然没有一次成功的步骤文件读取，即使 JSON 语法完全合法也无法通过证据检查；只读导航文件不够。只有在最终答案是强制作答时，操作的 `input` 才携带 `"forced": true`，而 `any_phase_forced` 会跨跟进保留更早的强制阶段。

## 跟进

Python 检查严格 JSON 形状和区间相对语义（精确 id 覆盖、动作锚点窗口、`none` 下锚点为空），并检查每个被引用的锚点及结构化 `evidence[].steps` 都指向保留对话中完整读取的步骤文本及其 manifest `result_sources` 结果章节（操作 `input` 中的 `read_steps`；目标投递已在开场输入中）。答案通过全部检查后不增加模型调用。

每个被拒的答案——JSON 格式错误、超出契约的取值、空的最终消息或缺少必读证据——都走同一种**跟进**：下一个运行器恢复完整 `job.history`，保留证据工具，并追加一条列出全部拒绝原因的消息（`prompts/injudge/agent/followup.md`）。跟进只修正所列问题，必要时读取所列文件，最多使用 `min(MAX_STEPS, 4)` 次调用；Python 再次校验新答案。

`MAX_ATTEMPTS`（默认 3）限制全部运行器阶段的总数。耗尽时保留可见错误和已打码的答案文本。不放宽解析器、不剥离格式包装作回退，也不对已合法答案追加模型调用。

输出上限截断的答案无法通过契约解析，会走纠正重试。超大轨迹意味着智能体按需选读证据文件夹。

## 失败处理

- 运行器层失败（子进程无法启动、非零退出、或写不出可读结果）是该区间的 `error` 判定并附 validation 注记；运行继续。不重试——相同的重试只会重付一次故障。缺少 Node、Node 低于 22.19、缺少运行器或 agent 包时，在准备输入前报出配置错误。配置检查使用已安装 pi 库提供的上下文预留。
- 智能体层错误（端点认证、持续传输失败）以运行结果的 `error` 字段出现，同样成为该区间的 error 判定。
- `TIMEOUT` 限制等待响应头或下一个正文块的空闲时间。持续返回数据的流可以运行更久，不设总耗时上限。在流式响应开始前，pi 可对暂时性请求故障重试最多两次，每次重试重新计时。流式响应开始后的故障不重试；服务端要求等待超过 60 秒后再重试时也会失败。`MAX_OUTPUT_TOKENS` 限制每次模型响应。

## 凭证

API key 和端点 URL 通过 `JUDGE_API_KEY`、`JUDGE_BASE_URL` 环境变量从 Python
传给运行器，两者都不作为配置字段写入作业或结果文件。端点路径可能包含凭证，
因此 URL 也需要这种保护。key 只发往配置的端点。回显 key 的端点输出会在进入判定、
`judge_raw` 或 validation 注记前打码，无论它来自 HTTP 错误还是成功响应。

打码覆盖原始 key 及其全部百分号编码拼写，包括两种十六进制大小写。
子进程不继承 `OPENAI_*` 或 `ANTHROPIC_*` 环境变量，防止这些变量改变提供方的请求头或端点。

加载评审凭证后，Python 在写入区间证据前打码；开场消息、证据哈希和读取检查使用
同一份已打码文件。报告、检查点记录、摘要和 HTML 也在保存前对已配置的密钥打码。
离线准备和 dry-run 不加载评审凭证。

打码也覆盖密钥本身的 JSON 序列化拼写。Python 在写入作业前对内容打码；运行器在序列化前对轨迹和结果中的字符串打码，因此进程停止也不会留下未打码的完整记录。打码不改变运行器当前对话中的文本。Python 随后再次检查已保存的轨迹，只解析 JSONL 外层并处理字符串字段，不解码字段内看似 JSON 的文本。

不完整或格式错误的记录会被移除，保留的轨迹以换行结束，确保下一次尝试可以安全追加；若无法保存打码后的轨迹，则删除该文件，并将区间记录为带有 input 诊断的错误。

每次读取为每个文件返回一个以 `==> path <==` 开头的文本块，`details.files` 给出逐文件元数据（`path`、`lines_read`、`line_start`、`line_end`、`truncated`，无法读取的路径则为 `error`），仅统计单次调用 200,000 字符上限内实际返回的文本；超出上限的文件标为未读。

`limit` 在文件最后一个非空行之前截止时，结果末尾会注明剩余行数与下一个 offset。分页读取可以合并；`read_steps` 证明完整步骤文本及 manifest `result_sources` 指向的投递结果章节均已返回；开场输入已有的目标投递无需重复读取。标题、截断行、搜索命中和回滚读取不算。

每份答案必须完整读取 manifest 中 `required_reads.always` 的文件：任务和基线文件、存在时的 `messages.md` 和 `gold.md`、首次消费步骤及同一 episode 内的前一步（若存在）；基线索引不代表其引用的文件已读；非空 novelty 与 acted_on 影响还须读取 `required_reads.prior_sources` 的全部条目，否则用 null。

none/referenced/selected 须检查完整条目窗口，acted_on 的非空效果还须检查至 episode 结束，因为后果可能晚于动作窗口出现。归因或效果未查明时用 influence 或 positive_effect null。完整读取并不证明判定本身正确。

先前来源包括基线中可见的其他投递的完整段落。manifest 提供
它们在 `deliveries.md` 中的行范围，开场消息也会列出；分页读取按步骤文件相同的规则合并覆盖。
目标文本已在开场消息中，不在该输入中的投递也不要求额外的基线读取。

读取达到字符上限时返回可继续读取的 offset 和 column。column 是首行内从 1
开始的 Unicode 字符位置，续段显示为 line@column: text。单个超长行也可以
分段读完；只有与原文匹配且仍保留的字符区间参与覆盖验证，缺口与回滚不计入。
